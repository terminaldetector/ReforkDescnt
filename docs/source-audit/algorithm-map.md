## `BitsAndChisels` · Greedy meshing микроблоков

**SOURCE PROJECT** `terminaldetector/BitsAndChisels` (CoolMineman), Fabric, коммит `abf3091`.
37 файлов, 2740 строк — весь мод.

**COMPONENT** `BitMeshes.createMesh` (285 строк), `BitsBlockEntity` (175), `BitNbtUtil` (96),
`BitsBlockModel` (132).

**PROBLEM SOLVED** Блок, разбитый на 16×16×16 подъячеек, каждая со своим материалом, должен
рисоваться без 4096 кубов на блок.

**ALGORITHM** Классический greedy mesher, три оси × два направления, послойно:

1. Для каждого из шести направлений и каждого из 16 слоёв заводится маска `used[16][16]`.
2. Идём по ячейкам слоя. Пропускаем воздух, уже занятое и то, чья грань не видна
   (`quadNeeded` — сосед в направлении грани непрозрачен).
3. От найденной ячейки растём по первой оси плоскости, пока состояние совпадает, ячейка свободна
   и грань нужна.
4. Затем растём по второй оси, на каждом шаге проверяя **всю** полосу, набранную на шаге 3.
5. Выпускаем один quad на получившийся прямоугольник, помечаем его в `used`.

Ключевая деталь — шаг 4 проверяет полосу целиком, а не только первую ячейку: иначе прямоугольник
может «съесть» дырку.

**DATA MODEL** `BlockState[16][16][16]` — 4096 ссылок на объект на каждый блок. Сериализация с
палитрой: `palette` (список уникальных состояний) + `bits_v2` (байтовый массив индексов), плюс
старый формат `bits` из `NbtList` коротких — палитра здесь именно то, что делает NBT приемлемым.

Меш отдаётся рендереру через `RenderAttachmentBlockEntity.getRenderAttachmentData()`, а модель
блока забирает его в `getBlockEntityRenderAttachment(pos)`. Это фабричный механизм передачи данных
блок-сущности в построение чанка — то есть меш строится **не** на рендер-треде кадра.

**WHY IT IS GOOD** Greedy meshing на 16³ убирает большую часть quad'ов: плоская стена из одного
материала становится одним прямоугольником вместо 256. Формат «палитра + индексы» делает и хранение,
и сеть дешёвыми ровно настолько, насколько мало материалов в блоке — а их обычно один-два.
`RenderAttachment` — правильный шов между данными блок-сущности и построением меша чанка.

**HOW TO ADAPT TO DRMD** Не заменой `MicroGrid`, а **вторым представлением рядом с ним.**

У DRMD уже есть микровоксели: `world/micro/MicroGrid`, 4³ = 64 ячейки в одном `long`, восемь байт
без аллокации, и это осознанный отказ от 16³ ради того, чтобы повреждаемым был каждый блок мира.
BitsAndChisels стоит на другом конце того же выбора: 4096 ссылок на блок — это десятки килобайт,
которые можно позволить себе на постройку и нельзя на весь рельеф.

Значит это не конкуренты, а разные задачи:

| | `MicroGrid` (есть) | Модель BitsAndChisels |
|---|---|---|
| Разрешение | 4³ = 64 | 16³ = 4096 |
| Материалы | один (материал самого блока) | свой на каждую ячейку |
| Цена | 8 байт, без аллокации | ~16–32 КБ на блок |
| Область | весь мир, разрушение | отдельные постройки |

Раздел 8 плана просит масштабируемость 8³ → 16³ → 32³ «без переписывания архитектуры». По этому
сравнению честный ответ — не единая структура на все случаи, а **общий интерфейс над двумя**:
дешёвая маска повреждений для рельефа и палитровая сетка для конструкций. Greedy mesher при этом
общий: он работает с «дай состояние в ячейке (x,y,z)», а откуда оно берётся, ему всё равно.

**Что брать целиком:** сам mesher (шаги 1–5) и формат «палитра + индексы». Лицензия позволяет
скопировать, но переписать под интерфейс выборки дешевле, чем адаптировать копию.

**Чего не брать:** коллизию. `rebuildShape` строит `BitSetVoxelSet(16,16,16)` из тех же данных, что
и рендер, то есть коллизия здесь равна визуалу в полном разрешении. Раздел 18 плана требует
обратного — разделить render / collision / navigation. У DRMD уже лучше: `CarvedBlock` кэширует
`VoxelShape` по маске в `ConcurrentHashMap`, то есть одинаковые формы считаются один раз на весь мир.

**DEPENDENCIES** Fabric Renderer API (`MeshBuilder`, `QuadEmitter`, `SpriteFinder`), Fabric
Rendering Data API (`RenderAttachmentBlockEntity`). Обе уже есть у DRMD через fabric-api. Один
миксин в вaниль (`SimpleVoxelShapeFactory`) — только ради коллизии, которая не переносится.

**LICENSE CONSTRAINTS** CC0-1.0. Отказ от прав, атрибуция не требуется. Единственный донор в
списке вообще без условий.

## `voxel-horizon-java-edition` · Стриминг, LOD и шов между ними

**SOURCE PROJECT** `terminaldetector/voxel-horizon-java-edition` (Oussama Aouessar), коммит
`06591b5`. **Не мод**: отдельный движок на Java 21 + LWJGL, 110 файлов, 17 573 строки. Чистое
разделение `core/` (мир, генерация, стриминг, математика) и `renderer/` (GL, меши, UI, камера).

**COMPONENT** `core/api/` (6 интерфейсов, 118 строк), `core/stream/RegionStreamingService` (328),
`core/world/LodTile` (75).

**PROBLEM SOLVED** Как отдать рендеру любой участок мира на любом расстоянии, никогда не блокируя
поток, который спрашивает, — и как сшить дальнее поле с ближним без швов.

### ALGORITHM — три решения, каждое переносимое отдельно

**1. Дальний LOD не зависит от кэша мира вообще.**

`LodProvider` документирован явно: тайлы считаются **напрямую из детерминированных колоночных
функций** (seed + координаты), без обращения к регионам и кэшу. Отсюда три гарантии — чистота
(одни и те же `seed, tile, step` всегда дают один тайл), потокобезопасность («никогда не блокирует
состояние мира, никогда не бросает исключение ни для каких координат»), и главная:

> Heights are byte-identical to the full-resolution region pipeline.

Высоты дальнего поля **побитово совпадают** с тем, что даст полный конвейер. То есть шов между LOD
и настоящим рельефом не сглаживается и не подбирается — его нет по построению. Цена: тайл с шагом
16 — «несколько сотен вычислений шума вместо полной сборки региона 288×288×6 слоёв».

**2. Кольцо соседей внутри тайла.**

`LodTile` хранит выборки на сетке `grid = cells + 3`: вершины `0..cells` плюс **одно лишнее кольцо**
с каждой стороны, индексы `i, j ∈ [-1, cells+1]`, адресация `index(i,j) = (j+1)*grid + (i+1)`.
Потребитель считает нормали и сшивает соседние тайлы **без единого дополнительного обращения**.

Это ответ на раздел 10 плана («shared border samples / ghost voxels / overlap sampling») в его
самой дешёвой форме: кольцо стоит `(cells+3)² − (cells+1)²` выборок, при `cells = 18` это 15%.

Данные — плоские примитивные массивы (`int[] height`, `int[] waterLevel`, `short[] topBlock`),
объект неизменяемый, `NO_WATER = Integer.MIN_VALUE` как сентинел.

**3. Спрашивающий никогда не ждёт.**

`RegionStreamingService` реализует сразу `ChunkProvider`, `WorldSampler` и `StreamingControl`.
Каждый запрос устроен одинаково:

```
region = ready.get(pos)
if (region == null) { scheduleRegion(pos); return детерминированная заглушка; }
return настоящий ответ
```

Заглушки осмысленные: `SEA_LEVEL` для высоты, биом 0, воздух для блока, `Chunk.emptyChunk` для
чанка. Никогда `null`, никогда исключение, никогда ожидание.

Три `ConcurrentHashMap` держат состояние: `ready` (готовые регионы), `inFlight`
(`CompletableFuture<Region>` — дедупликация одновременных сборок одного региона), `chunkCache`
(производные чанки). Пул — фиксированный, `CPU_WORKERS` потоков, с именованной фабрикой
(`region-gen`), то есть в профайлере видно, чей это поток.

**Вытеснение отменяет работу, а не только выбрасывает результат.** `evictOutside` проходит по
`inFlight` и вызывает `future.cancel(true)` для регионов, вышедших из радиуса, — сборка, которая
уже никому не нужна, не досчитывается до конца.

**DATA MODEL** Правки игрока живут **отдельно от генерации**:
`blockEdits: chunkKey -> (columnIndex*height + y -> blockId)`, применяются `applyEdits(chunk)`
**после** детерминированной сборки. Поэтому генерация остаётся чистой, а правки переживают
вытеснение и пересборку региона. `setBlock` при этом ещё и мутирует живой чанк в кэше, «чтобы
физика и меширование увидели изменение немедленно».

**WHY IT IS GOOD** Разделение «чистая генерация + наложенные правки» — это то, что делает всё
остальное возможным: чистую часть можно считать на любом потоке, в любом порядке, сколько угодно
раз, и она же даёт побитовое совпадение дальнего поля с ближним. Интерфейсы в `core/api`
(`WorldAccess` как запись из пяти сервисов) — тот самый шов из раздела 4 плана: рендер разговаривает
с ядром через них и не знает про регионы, кэш и потоки.

### HOW TO ADAPT TO DRMD

**Это ответ на задачу «вынести перестройку горизонта с рендер-треда».**

Сейчас `PlanetClientState.mesh(...)` строит поле синхронно внутри кадра — измерено 14 перестроений
за сессию, худшая 26 мс, то есть пропущенный кадр. Схема выше переносится почти дословно:

| Здесь | У DRMD сейчас | Что делать |
|---|---|---|
| `ready` / `inFlight` / пул `region-gen` | синхронная сборка в кадре | пул `drmd-horizon`, поле `volatile mesh`, дедуп по поколению |
| детерминированная заглушка | `null` до первой сборки | рисовать прошлое поле, пока строится новое |
| `future.cancel(true)` при вытеснении | — | отменять сборку, если камера ушла |
| чистая генерация + наложение правок | сборка **читает** `PlanetClientState.INSTANCE.observedHeight(...)` | вот это и есть препятствие |

Последняя строка — главное. `PlanetSurfaceMesh.build` принимает `seed` и снаружи выглядит чистой,
но внутри (`PlanetSurfaceMesh:194, 203, 396`) обращается к `PlanetClientState.INSTANCE` за
наблюдённой высотой и цветом, то есть к общему `SurfaceStore`, который пишет сетевой поток. Это
ровно то смешение, которого движок избегает разделением на чистую генерацию и наложенные правки.

`SurfaceStore` уже потокобезопасен (`ConcurrentHashMap`, `synchronized (residency)`,
`ConcurrentHashMap.newKeySet()`), так что чтение с рабочего потока безопасно **сегодня**. Но
`scars` — обычный `HashSet`, который мутирует сетевой поток, и вот его надо заменить на
`ConcurrentHashMap.newKeySet()` перед выносом сборки.

**Кольцо соседей стоит взять в `SurfaceSection`.** У DRMD секция 32×32 без кольца, поэтому сшивку
колец `HorizonGrid` делает сам. `grid = cells + 3` убирает эту работу и заодно даёт нормали.

**Побитовое совпадение — цель, а не данность.** У DRMD дальнее поле процедурное, а ближнее
приходит с сервера; совпадение по построению здесь недостижимо. Но требование стоит записать в
обратную сторону: процедурная функция должна быть **той же самой**, что генерирует рельеф на
сервере, иначе шов на границе наблюдённого неизбежен.

**DEPENDENCIES** LWJGL — только в `renderer/`. `core/` зависит лишь от JDK: `java.util.concurrent`,
примитивные массивы, записи. Переносится без единой сторонней библиотеки.

## `Valkyrien-Skies` (VS1) · Твёрдое тело: масса, тензор инерции, силы, моменты

**SOURCE PROJECT** `terminaldetector/Valkyrien-Skies`, коммит `2de196b` («EOL notice»). Minecraft
1.12, Forge, 235 файлов. Устарела интеграция с игрой; модель твёрдого тела — нет.

**COMPONENT** `physics/PhysicsCalculations` (544 строки), `ships/physics_data/ShipInertiaData` (22),
`ShipPhysicsData` (24), `BasicCenterOfMassProvider` (95),
`ships/ship_transform/CoordinateSpaceType` (13), `util/multithreaded/VSWorldPhysicsLoop` (267).

**PROBLEM SOLVED** Как из набора блоков Minecraft получить тело, которое движется и вращается от
приложенных сил и моментов, а не от присвоенной скорости.

### DATA MODEL — ровно то, что план требует в разделе 5

```
ShipInertiaData   gameTickMass          double
                  gameMoITensor         Matrix3dc   (3x3, в собственных осях тела)
                  gameTickCenterOfMass  Vector3dc

ShipPhysicsData   linearVelocity        Vector3dc
                  angularVelocity       Vector3dc

CoordinateSpaceType  GLOBAL_COORDINATES | SUBSPACE_COORDINATES
```

Всё на **JOML** — `Matrix3d`, `Vector3d`, `Quaterniond`, `AxisAngle4d`. У DRMD JOML уже на classpath
(`org.joml.Matrix4f` в порталах), то есть новой зависимости не появится.

`CoordinateSpaceType` — это ровно `D6Space` из раздела 14 в зачаточной форме: перечисление из двух
значений, которым сущность отвечает на вопрос «я сейчас в локальных координатах или в мировых».

### ALGORITHM

**1. Тензор инерции из блоков — параллельные оси, дважды.**

`BasicCenterOfMassProvider.addMassAt` при добавлении массы в точке пересчитывает **и** центр масс,
**и** тензор за один проход: сначала новый центр как взвешенное среднее, затем перенос уже
накопленного тензора на сдвиг центра (`cmShift`) плюс вклад новой точки относительно нового центра.
В исходнике сослались на вывод: `kwon3d.com/theory/moi/triten.html`, уравнения 13 и 14.

Диагональ: `I₀₀ += (Δy² + Δz²)·M + (ry² + rz²)·m`, и так по трём осям. Внедиагональные:
`I₀₁ -= Δx·Δy·M + rx·ry·m`, тензор симметричен (`[3]=[1]`, `[6]=[2]`, `[7]=[5]`).

Важная деталь: блок добавляется **не одной точкой в центре, а восемью по углам** со смещением
`INERTIA_OFFSET = 0.4`. Точечная масса имеет нулевой собственный момент, и одиночный блок тогда
вращался бы вокруг себя без сопротивления; восемь точек дают блоку настоящий тензор.

**2. Тензор в мировые оси — каждый физический тик.**

```
I_world     = R · I_body · Rᵀ
I_world⁻¹   = invert(I_world)
```

Пересчитывается каждый тик, потому что `R` меняется. `I_body` при этом постоянна, пока не изменился
состав тела, — именно ради этого она и хранится в собственных осях.

**3. Сила в точке → момент.**

```
τ += (r × F) · dt
F_total += F · dt
```

где `r` — от **центра масс**, не от якоря. Умножение на `dt` внутри аккумулятора означает, что
накапливаются импульсы, а не силы; знать это обязательно, иначе шаг 4 даёт неверную размерность.

**4. Интегрирование.**

```
ω += I_world⁻¹ · τ ;  τ := 0
v += F_total / m   ;  F_total := 0
x += v · dt
```

**5. Поворот — через кватернион, и умножение слева.**

```
если |ω|² < .001            → поворот не изменился, выходим
если |ω| > максимума        → нормировать и умножить на максимум
axisAngle = AxisAngle4d(|ω| · dt, ω̂)
rotation  = premul(Quaterniond(axisAngle), rotation).normalize()
```

**`premul`, а не `mul`** — угловая скорость здесь в мировых осях, поэтому приращение поворота
применяется слева. Это ровно та деталь, которую план в разделе 3 велит записывать, а не
восстанавливать по памяти: перепутанный порядок даёт вращение, выглядящее правдоподобно и неверно.

Нормировка после каждого шага — против накопления ошибки в кватернионе.

**6. Скорость точки тела.** `v_point = ω × r + v`.

**7. Численная устойчивость** названа явно: `EPSILON = 1e-8`, `DRAG_CONSTANT = .99`, отдельный
`isPhysicsBroken()`, потолки линейной и угловой скорости, ограничение по Y. Масса ниже `0.0001`
обнуляется, «чтобы не делить на ноль».

**8. Физика в своём потоке.** `VSWorldPhysicsLoop` — обычный `while (threadRunning)` с замером
`System.nanoTime()` до и после тика и `Thread.sleep` на остаток идеального интервала; если физика
выключена — сон 100 мс, «иначе этот while(true) съедает кучу CPU». Список кораблей берётся снимком
(`getAllLoadedThreadSafe`).

### HOW TO ADAPT TO DRMD

**Это спецификация PHASE 1, и она несовместима с тем, что есть.**

`ShipAttitude` хранит ориентацию парой ортонормированных векторов forward/up и поворачивает её
инкрементами `pitchLocal` / `yawLocal` / `rollLocal`; `FlightSystem` заканчивается на
`player.setVelocity(...)`. Ни массы, ни тензора, ни угловой скорости как состояния. Переход — замена
ядра управления, а не рефакторинг, и всё, чем настроено ощущение полёта (тиры афтербёрнера,
`docs/AFTERBURNER_TIERS.md`), придётся перевыразить в силах и моментах.

Порядок, который следует из этого разбора:

1. `D6PhysicsBody` со состоянием ровно как выше: масса, `I_body`, центр масс, `v`, `ω`, кватернион
   поворота, аккумуляторы силы и момента. Чистый класс на JOML, без Minecraft — то есть тестируемый
   так же, как `ObliqueNearPlane` и `PortalCrossing`.
2. Тесты из раздела 23 плана пишутся прямо по шагам 1–6: свободный полёт, гравитация, сила, момент,
   roll/pitch/yaw, сохранение углового момента.
3. `ShipAttitude.forward/up` становится представлением кватерниона, а не состоянием.
4. `FlightSystem` начинает выдавать силу и момент вместо скорости.

**Чего не брать.** Всю интеграцию с Minecraft 1.12 — она устарела целиком. Lombok (`@Data`) и
аннотации Jackson — в DRMD их нет и заводить незачем. `addForceAtPoint` в двух `@Deprecated`
вариантах — брать только `addForceAtPointNew`.

**Оговорка про шаг 3.** Умножение на `dt` внутри аккумулятора — это выбор VS, а не единственный
вариант; чище хранить силу и момент, а `dt` применять при интегрировании. Если делать по-своему,
шаг 4 меняется соответственно, и об этом стоит помнить при чтении их кода.

**DEPENDENCIES** JOML (уже есть). Lombok и Jackson — только в обвязке, в саму математику не входят.

**LICENSE CONSTRAINTS** Apache-2.0. Копировать можно с сохранением NOTICE и указанием изменений.
Но для 1.12-классов с lombok и чужими родителями своя реализация по описанию выше чище копии — и
именно поэтому описание здесь такое подробное.

## `portal-gun-mod` · Куда поставить портал

**SOURCE PROJECT** `terminaldetector/portal-gun-mod`, ветка `1.21.1`, MIT (MeowMC 2021,
Jozef 2025). 26 файлов, 2972 строки. **NeoForge**, не Fabric.

**COMPONENT** `PortalGunItem.findPortalPlacement` (403 строки на весь класс), плюс
`PortalGunMod.isAreaClear` / `isWallValid`.

**PROBLEM SOLVED** Игрок стреляет в стену — где именно и как повёрнутый окажется прямоугольный
портал.

**ALGORITHM**

1. Луч даёт блок и грань. Портал ставится в **соседнюю воздушную** клетку:
   `hit.getBlockPos().relative(hit.getDirection())`, а `wallFacing` — сама грань.
2. **Луч, прошедший сквозь портал, учитывается.** Результат трассировки несёт список пройденных
   порталов, и через каждый из них сворачиваются (`reduce`) и направление гравитации игрока, и его
   вектор взгляда. То есть выстрел *через* портал ставит портал правильно на той стороне. Это та
   часть, которую не придумаешь, пока не столкнёшься.
3. Гравитация и `wallFacing` переводятся в локальную систему игрока (мод поддерживает смену
   гравитации).
4. Кандидаты на «верх» портала — четыре направления, перпендикулярные оси стены.
5. **Кандидаты сортируются**: локальный `UP` получает высший приоритет константой, остальные —
   по горизонтальному скалярному произведению с вектором взгляда. Портал старается встать «верхом
   вверх», а если нельзя — повернуться по взгляду.
6. Для каждого кандидата строится `AARotation.getAARotationFromYZ(upDir, wallFacing)`, ею
   поворачивается размер портала `(width, height, 1)`, из этого получается `IntBox` области, а
   `wallBox` — та же коробка, сдвинутая на шаг в стену.
7. Кандидат принимается, если область пуста, стена целая и в этой области ещё нет портала.

**DATA MODEL** `record PortalPlacement(AARotation rotation, IntBox areaBox, IntBox wallBox)`.
`COOLDOWN_TICKS = 4`.

**WHY IT IS GOOD** Пункты 2 и 5 — это то, что отличает работающую пушку от демки. Первый делает
порталы композируемыми (стрелять сквозь них), второй убирает главный источник раздражения: портал,
вставший боком.

**HOW TO ADAPT TO DRMD** У DRMD `PortalGunItem` ставит панель по грани без выбора ориентации, и
`PortalPanelBlock.FACING` берётся прямо из `ctx.getSide()`. Пункты 4–7 переносятся почти дословно.

Отдельно стоит отметить, **чем этот алгоритм подтверждает вчерашние решения по вендорингу**: он
целиком стоит на `AARotation.getAARotationFromYZ` и на `IntBox`. Первое перенесено сегодня как
`ImmPtlAARotation.fromYZ`; второе было отложено как «нет вызывающих» — теперь вызывающий есть, и
`IntBox` возвращается в очередь на перенос.

Пункт 5 у DRMD осмысленно меняется: в игре с 6DoF «локальный верх» это не мировой `UP`, а ось
корабля. Кандидатов надо сортировать по ориентации тела (`D6PhysicsBody.rotation()`), а не по
гравитации — иначе портал, поставленный в перевёрнутом полёте, встанет вверх ногами относительно
пилота.

**DEPENDENCIES** Immersive Portals — весь мод является его надстройкой; вспомогательные классы
ImmPtl (`AARotation`, `IntBoxHelper`, `IPGlobalHelper`, `CollisionHelperUtil`) скопированы внутрь
под своим пакетом, потому что Forge-порт ImmPtl их не экспортирует. Плюс GeckoLib для анимации и
Gravity Changer.

Это, кстати, подтверждает разделение из §2 брифа на практике: **портальная пушка — клиент движка**.
Из 2972 строк собственно пушке принадлежит один класс.

**LICENSE CONSTRAINTS** MIT. Копировать можно с сохранением копирайта. Код под NeoForge, то есть
переносится идея и структура, а вызовы — переписываются под Fabric.

## `Eureka` · Сборка и разборка корабля — и поправка к моему же выводу

**SOURCE PROJECT** `terminaldetector/Eureka`, коммит `07cf418`, Apache-2.0. 56 файлов, 3962 строки,
почти весь Kotlin. Тонкая надстройка над VS2: собственно кораблём занимается ядро VS, Eureka даёт
блоки, руль, двигатели и управление.

**COMPONENT** `util/ShipAssembler.kt` (231 строка), `ship/EurekaShipControl.kt` (469).

**PROBLEM SOLVED** Как набор блоков в мире становится движущимся телом и как возвращается обратно.

### Поправка к базовой карте

В [`drmd-baseline.md`](drmd-baseline.md) я записал, что подвижные структуры DRMD «двигаются
перезаписью блоков в мире — то, что план в §21 называет `teleport как замена physics`». Формулировка
была слишком широкой, и донор это показывает.

**Valkyrien Skies тоже перезаписывает блоки.** `unfillShip` возвращает корабль в мир, проходя все его
чанки, все секции, все 16×16×16 ячеек и вызывая `relocateBlock` на каждый непустой блок. Разница не
в том, что перезаписи нет, а **когда** она происходит: у VS это один раз при сборке и один раз при
разборке, а между ними корабль живёт в собственном пространстве координат со своей физикой. У DRMD —
на каждое перемещение.

Запрещено планом не «переписывать блоки», а «переписывать вместо того, чтобы иметь тело». Разница
существенная, и она задаёт форму PHASE 2: нужен не другой способ двигать блоки, а отдельное
пространство, куда они переносятся один раз.

### Три приёма, которые стоят переноса

**1. Поворот прижимается к 90° при разборке.** `snapRotation` берёт `AxisAngle4d` корабля, выбирает
доминирующую ось (наибольшая по модулю компонента) и округляет угол до кратного `PI/2`; затем
`rotationFromAxisAngle` переводит это в ванильный `Rotation`, отказываясь (возвращая `NONE`) от
любого поворота, чья ось не Y.

Причина очевидна и всё же её легко забыть: **блок умеет стоять только в осевых ориентациях**.
Корабль под 37° кладёт свои блоки под 0°. Это ровно то, для чего нужна группа из 24 поворотов, и
подтверждение, что `ImmPtlAARotation` перенесён не зря — только там она полная, а здесь урезана до
четырёх поворотов вокруг Y.

**2. Клиенту говорят не обновлять чанки, пока идёт запись.** `PacketStopChunkUpdates` со списком всех
затрагиваемых чанков — до, `PacketRestartChunkUpdates` — после, причём второе отложено до момента,
когда все чанки станут тикающими (`level.server.executeIf { chunkPoses.all(level::isTickingChunk) }`).
Без этого игрок видит, как структура растворяется и появляется поблочно.

**3. Сначала пишутся все состояния, потом рассылаются обновления.** Комментарий в исходнике: «We
update the blocks after they're set to prevent blocks from breaking». Факел, поставленный раньше своей
стены, отваливается; два прохода это убирают.

### HOW TO ADAPT TO DRMD

`StructureMover.place` пишет `world.setBlockState(..., Block.NOTIFY_LISTENERS)` в одном цикле. Флаг
без `NOTIFY_NEIGHBORS`, поэтому соседские обновления не идут и пункт 3 сегодня не кусается — но и
пункт 2 не сделан, а он про то, что видит игрок.

Порядок работ для PHASE 2 из этого чтения:

1. Локальное пространство структуры — то, чего нет вовсе и без чего остальное бессмысленно.
2. Перенос в него и обратно, один раз, с прижатым к осям поворотом (`ImmPtlAARotation`).
3. Отложенные обновления чанков у клиента на время переноса.

**DEPENDENCIES** VS2 целиком — Eureka без него не существует. Kotlin. Для DRMD это означает чтение
как описания: Apache-2.0 разрешает копировать, но перевод Kotlin в Java для 231 строки дороже, чем
написать по разобранному алгоритму.

**LICENSE CONSTRAINTS** Apache-2.0, с NOTICE и указанием изменений при копировании.

## `Eureka` · Управление: как ввод пилота становится моментом

**COMPONENT** `ship/EurekaShipControl.kt`, 469 строк. Тот же проект и та же лицензия, но задача
другая, поэтому отдельной записью.

**PROBLEM SOLVED** У плана есть разрыв, названный прямо: AI и навигация выдают *желаемую скорость*
(§16, §17), а физика принимает *силу и момент* (§9). Между ними ничего нет. Здесь есть.

### ALGORITHM

**1. Желаемое угловое ускорение умножается на тензор инерции.**

```
physShip.applyWorldTorque(moiTensor.transform(Vector3d(0, idealAlphaY, 0)) + banking)
```

Это и есть мост. Пилот задаёт, **с каким ускорением** повернуть; τ = I·α переводит это в момент.
Следствие, ради которого так и делают: корабль поворачивается с одинаковой скоростью независимо от
массы — ввод отображается в ощущение, а не в силу.

**2. Предел поворота задаётся размером корабля, а не константой.**

```
largestDistance = самый дальний горизонтальный угол AABB от центра, зажатый в [0.5, maxSize]
maxOmegaY = maxLinearSpeed  / largestDistance
maxAlphaY = maxLinearAccel  / largestDistance
```

Потому что `a = α·r`: большой корабль на той же угловой скорости швыряет свои оконечности быстрее.
Ограничивается **скорость кончика**, а не угловая скорость. Физически мотивировано и снимает
необходимость подбирать отдельную константу на каждый размер корпуса.

**3. Тот же канал служит тормозом.**

```
normalizedAlphaYMultiplier =
    если (ниже предела и есть ввод) → ввод
    иначе                           → -omega.y зажатый в [-1, 1]
```

Одно выражение: есть ввод и есть запас — разгоняем; нет ввода или превышен предел — гасим. Не
отдельная система демпфирования, которая может разойтись с разгоном.

**4. Крен выводится из поворота, а не задаётся отдельно.** `getPlayerControlledBanking(..., -idealAlphaY)`
— момент крена пропорционален угловому ускорению рыскания, повёрнут в систему корабля, Y обнулён.
Пилот не кренит: он поворачивает, крен появляется сам.

**5. Вертикаль — сервопривод по скорости с упреждением по гравитации.**

```
idealUpwardForce = (idealVy - vy - GRAVITY/snappiness) * mass * snappiness
```

Пропорциональный регулятор по скорости, домноженный на массу, чтобы отклик не зависел от неё, с
вычетом гравитации, чтобы удерживать высоту без установившейся ошибки. Плюс явное сопротивление
`vel.y * -mass`.

**6. Насыщающие кривые вместо обрезки.** `smoothing(s, max, x) = max - s/(x + s/max)` и
`smoothingATan(s, x) = atan(x*s)/s` — ввод подходит к пределу плавно, а не упирается в него.

### HOW TO ADAPT TO DRMD

**Это ровно та половина PHASE 1, которой не хватало.** `D6PhysicsBody` принимает силы и моменты;
`FlightSystem` сегодня выдаёт скорость. Пункт 1 — переходник между ними, и он же переходник для
`D6 Nav` и AI из §16–17 плана: желаемая величина умножается на инерцию и становится моментом.

Пункт 2 переносится с поправкой на 6DoF: у Eureka ограничение только по Y, потому что корабль
плавает и не кувыркается. У DRMD три оси, поэтому предел считается по трём — но по тому же правилу
«ограничиваем скорость кончика», и `largestDistance` берётся из того же AABB.

Пункт 3 стоит взять дословно: у DRMD сейчас `flightAssist` отдельным флагом, а это делает
демпфирование частью того же выражения, что и разгон.

Пункт 4 в 6DoF теряет смысл в исходном виде (крен — самостоятельная ось управления), но идея
«производная ось выводится из основной» пригодится там, где нужен автоматический доворот.

### РЕАЛИЗОВАНО

`src/main/java/com/terminaldetector/drmd/d6/D6FlightControl.java` — по этому разбору, без единой
строки донора. Соответствие пунктам:

| Пункт | Метод | Отличие от Eureka |
| --- | --- | --- |
| 1. τ = I·α | `steer` | тензор берётся мировой (`worldInertia`), а не только Y-компонента |
| 2. Предел от размера | `steer`, параметры `radius`/`maxTipSpeed`/`maxTipAcceleration` | по трём осям вместо одной; `reach` зажат снизу на 0.5 |
| 3. Разгон и торможение одним выражением | `axisAcceleration` | дословно |
| 5. Сервопривод по скорости | `holdVelocity`, `holdVelocityAgainst` | упреждение вынесено в параметр, а не зашито гравитацией |
| 6. Насыщающая кривая | `saturate` | перенесена только `atan`-версия; гипербола `max - s/(x + s/max)` не понадобилась |

Пункт 4 (крен из рыскания) **не перенесён** намеренно: в 6DoF крен — самостоятельная ось
управления, и выводить его из поворота значило бы отнять у пилота ось. Идея остаётся в записи выше
на случай автодоворота.

`thrust` — не из этого списка: у Eureka продольная тяга размазана по режимам, у DRMD это один
метод, домноженный на массу по тому же принципу, что и пункт 5.

Проверено `src/test/java/com/terminaldetector/drmd/D6FlightControlTest.java`: тензор мировой, а не
телесный (тот же ввод на накренённом корпусе даёт другой момент); за пределом скорости торможение
перебивает полный ввод; просадка пропорционального сервопривода под тяжестью равна `g/gain`, и
упреждение убирает её до нуля.

**LICENSE CONSTRAINTS** Apache-2.0. Код на Kotlin, то есть переносится описание: перевод 469 строк
дороже, чем реализация по разобранным шести пунктам.

## `Clockwork` — кто и когда имеет право трогать физическое тело

**SOURCE PROJECT** `terminaldetector/Clockwork`, Apache-2.0, 589 файлов на Kotlin. Надстройка над
VS2, как и Eureka, но задача другая: не «управлять кораблём», а «подключить к нему источники силы».

**PROBLEM SOLVED** У DRMD `D6PhysicsBody` есть аккумуляторы силы и момента — и нигде не сказано,
**кто** и **из какого потока** имеет право в них писать. Здесь на это отвечено.

### 1. Архитектура: очереди, а не прямые вызовы

`MultiInstanceForceApplier` — вложение на корабль, держащее карту источников силы. Меняется она
только через три конкурентные очереди, и разбираются они **в начале физического тика**:

```kotlin
override fun physTick(physShip: PhysShip, physLevel: PhysLevel) { pollChanges() }

fun createApplier(createData: C): Int { … createdAppliers.add(id to createData); return id }
fun updateApplier(id: Int, updateData: A)  { applierUpdateData.add(id to updateData) }
fun removeApplier(id: Int)                 { removedAppliers.add(id) }
```

Игровой поток (блок-сущности, ввод, сеть) **никогда не трогает тело**: он кладёт в очередь. Физика
разбирает очередь ровно в одной точке и дальше работает со снимком. Идентификатор возвращается сразу,
до применения, — поэтому вызывающий может отменить то, что ещё не создалось.

Это и есть недостающая половина границы из §9 плана. У DRMD сформулировано «физика принимает только
силы и моменты», но не сформулировано, что вызов должен быть отложенным. Без этого первый же
пропеллер, поставленный из блок-сущности, окажется гонкой.

### 2. Сила прикладывается в точке блока, а не к центру масс

```kotlin
if (physData.brass) physShip.applyWorldForceToBodyPos(force)
else                physShip.applyWorldForceToModelPos(force, Vector3d(physData.position).add(0.5, 0.5, 0.5))
```

Две разные функции для двух разных смыслов: к центру масс — только толкает, в точку — толкает и
поворачивает. У DRMD это `applyForce` и `applyForceAtPoint`, уже есть; отсутствует привычка выбирать
между ними осознанно.

И скорость, по которой считается аэродинамика, — это скорость **точки**, а не корабля:

```kotlin
val totalVelocityAtProp = physShip.velocity.add(wind).add(
    physShip.angularVelocity.cross(propPosition.sub(physShip.centerOfMass)))
```

То есть `v + ω × r` — ровно `D6PhysicsBody.velocityAtPoint`, плюс ветер.

### 3. Пропеллер: теория элемента лопасти, а не «тяга = обороты»

Для каждой лопасти:

```
φ   = atan2(осевая скорость, окружная скорость)     — угол притока
α   = шаг лопасти − φ                                — угол атаки
Cl  = 2π·α                                           — тонкий профиль
Cd  = 0.01 + 0.01·Cl²                                — паразитное плюс индуктивное
q   = ½·ρ(y)·V²                                      — скоростной напор
dT  = (Cl·q·dA·cos φ − Cd·q·dA·sin φ)
```

Три вещи в этом важнее самой формулы.

**Плотность и температура воздуха зависят от Y** — `aerodynamicUtils.getAirDensityForY(y, dimension)`.
Тяга винта падает с высотой сама, без отдельного правила. Для игры про полёт от земли до орбиты это
именно то, что должно делать пропеллер бесполезным наверху, а ракету — нет.

**Плавный выход на режим.** Ниже минимальной окружной скорости тяга не обрезается, а гасится
`smoothstep`: `sf = s²(3−2s)`. Резкий порог на малых оборотах читается как рывок.

**Спад у скорости звука.** `1 − 1/(1 + exp((331 − |v|)/30))` — логистическая функция, обнуляющая тягу
к 331 м/с. Плюс жёсткий клэмп модуля силы и момента в конце. Оба — защита от того, что игрок
построит машину, вылетающую за пределы модели.

### 4. Маховик: чистый момент без силы

```kotlin
physShip.applyWorldTorque(
    shipToWorld.transformDirection(data.direction).normalize().negate()
        .mul(data.currentRPM * wheelMass))
```

Пятьдесят две строки на весь класс. Ось задана **в системе корабля** и поворачивается в мировую;
знак отрицательный, потому что корабль получает реакцию, а не вращение колеса. Для 6DoF это
единственный способ менять ориентацию без выхлопа, и он тривиален — что стоит записать, потому что
выглядит сложнее, чем есть.

### 5. Подшипник: третий закон Ньютона, записанный явно

```kotlin
if (physShipBearingIsOn == null) {          // другой конец — мир
    physShip.applyWorldTorque(torque)
} else {
    physShip.applyWorldTorque(torque)
    physShipBearingIsOn.applyWorldTorque(torque.mul(-1.0, Vector3d()))
}
```

Момент прикладывается к **обоим** телам, равный и противоположный; если другой конец — неподвижный
мир, реакция уходит в него и второго вызова нет.

И отдельно: **заблокированный подшипник вообще не создаёт момента** — `if (data.kinematic) continue`,
потому что он реализован фиксированным соединением с целевым углом. Один блок, два разных механизма
в зависимости от режима: связь, когда угол задан, сила — когда задана скорость.

**HOW TO ADAPT TO DRMD** Пункт 1 переносится как правило, а не как код: любой источник силы,
живущий в блок-сущности, обязан класть в очередь. Пункт 3 переносится целиком, если у DRMD появится
атмосфера с плотностью по высоте — а она нужна и для других целей. Пункты 4 и 5 — это спецификация
того, чего у `D6PhysicsBody` нет: тело одно, второго конца связи приложить некуда. Связи между
телами — отдельная задача, и её стоит завести, а не откладывать до первого крана.

## `NoCubes` — гладкий рельеф, и почему столкновения дороже отрисовки

**SOURCE PROJECT** `terminaldetector/NoCubes`, **LGPL-3.0** — только описание, копировать нельзя.
8444 строки без тестов и миксинов.

**PROBLEM SOLVED** §9 брифа: рельеф перестаёт быть кубическим. Здесь есть и то, как это рисуется, и
— что важнее — во что это обходится физике.

### 1. Поле расстояний строится «неправильно», и это осознанно

Surface Nets ждёт знаковое расстояние **в углу** блока. Получить его можно, усреднив плотности блока
и его соседей. Донор так **не делает**, и объясняет почему:

> Doing this results in loss of terrain features (one-block large features effectively disappear).
> Because we want to preserve these features, we feed SurfaceNets the inverted block densities,
> pretending that they are the corner distances and then offset the resulting mesh by 0.5.

То есть в поле кладутся значения из **центров** ячеек, алгоритму говорится, что это углы, а
результат сдвигается на полблока. Математически это не то, что просит алгоритм; зато одиночный блок
остаётся виден. Правильный вариант тоже есть — `generateAveragedDistanceField` под флагом
`smoothness2x`, — и оба сохранены, потому что это выбор между гладкостью и деталью, а не баг.

**Это ровно тот компромисс, который придётся принять DRMD**, и лучше принять его сознательно: в
воксельном мире «сглаживать честно» значит стирать всё размером в один блок, а в игре про стрельбу
одиночный блок — это укрытие.

### 2. Область нужна с запасом, иначе швы

`getPositiveAreaExtension` = 1 блок, `getNegativeAreaExtension` = 1 или 2 — потому что Surface Nets
выдаёт сетку на единицу меньше области. Комментарий донора про отрицательное расширение честен: «I'm
not sure why it's needed, but it is needed very much». Практический вывод для нас: **любая гладкая
геометрия требует читать соседей за границей чанка**, и это надо закладывать в стриминг, а не
обнаруживать по швам.

### 3. Столкновения: гладкая сетка коллайдером не становится

Самое ценное здесь. Minecraft умеет сталкивать только с AABB, поэтому **каждая грань гладкой сетки
превращается в набор осевых коробок**, и способов два, оба включены одновременно:

```java
// на вершину — коробка от вершины до (центр + нормаль)
return consumer.accept(
    min(vX, centre.x + faceNormal.x), min(vY, …), min(vZ, …),
    max(vX, centre.x + faceNormal.x), max(vY, …), max(vZ, …));
```

и «старый стиль» — кубики радиусом `0.125` в четырёх вершинах, в центре, затем в серединах рёбер,
числом по настраиваемому `oldStyleCollisionsEnhancementLevel`. Лестница из мелких коробок вместо
поверхности.

**Вывод, ради которого это стоило читать:** нарисовать гладкий рельеф — дешёвая половина; *столкнуть*
с ним — дорогая. Либо N коробок на грань в ванильной системе, либо своя система столкновений. У
DRMD с его 6DoF и скоростями второе, вероятно, неизбежно, и решать это надо **до** того, как
появится гладкая геометрия, а не после.

**HOW TO ADAPT TO DRMD** Алгоритм переносится только описанием (LGPL). Surface Nets — общественное
достояние по существу (Mikola Lysenko, 2012), и брать надо его, а не этот порт. Из порта берутся три
вывода: компромисс с полем расстояний (пункт 1), запас области (пункт 2) и цена столкновений
(пункт 3). Третий — самый важный, и он архитектурный, а не про геометрию.
