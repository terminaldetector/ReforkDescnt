6. Исправления должны быть небольшими, проверяемыми, с регрессионными тестами. Не удаляй проверки или не ослабляй численные пороги ради зелёного CI.
7. Не останавливайся после компиляции, если программа не запустилась в реальном клиенте. Действительным результатом считается **работающий тестовый клиент + достоверные доказательства**.

## 1. Где оборвалась предыдущая сессия

В последнем сохранённом сообщении предыдущего агента указано:

> Компиляция уже up-to-date; сейчас один раз докачиваются vanilla assets для реального клиента. Это последний инфраструктурный слой после очистки. После него вывод станет смысловым: либо сцена проходит до `swarm-ai-ok.txt`, либо получим точный assert по синхронизации/движению. Клиентская цепочка уже вошла в повторный GameTest; ошибка запроса Yggdrasil-ключа ожидаема для офлайн disposable-мира и не участвует в тестах. Важно: сервер загрузил именно текущий мод, 22 теста сейчас выполняются перед копированием мира в rendercheck.

**Осторожная интерпретация:** компиляция была up-to-date; тестовый сервер стартовал; очередные 22 GameTest начали выполнение; клиентские vanilla assets докачивались. Сообщение НЕ подтверждает итоговое прохождение этих 22 GameTest, rendercheck или появления `swarm-ai-ok.txt`. Это **обрыв контекста**, а не свидетельство конкретного провала тестов.

Исторически в переписке сообщалось о проходе **480 unit-тестов и 22 GameTest**, но это данные прежнего прогона, а не сертификат текущего SHA. Проверить фактические XML/JUnit/CI-отчёты.

### Почему GameTest повторяется

Факт из `build.gradle`:

```groovy
tasks.register('prepareRendercheckWorld', Sync) {
    dependsOn runGametest
    from 'build/gametest/world'
    into 'build/rendercheck/saves/DRMD-render-lab'
    exclude '**/session.lock'
    // validates level.dat and writes rendercheck options.txt
}
tasks.named('runRendercheck') { dependsOn prepareRendercheckWorld }
```

То есть при `runRendercheck` Gradle должен подготовить одноразовый мир и при необходимости вызвать `runGametest`. Повторный прогон **сам по себе** не регрессия. Установи, действительно ли Gradle повторно выполняет задачу, подхватывает старый fixture или застревает внутри клиента.

### Что считать информационным шумом, а не блокером

- Запрос Yggdrasil/auth key в офлайн тестовом окружении может завершаться ошибкой при сохранении корректного запуска сервера. Не отключай глобальную авторизацию, не патчи безопасность и не меняй production-auth ради подавления сообщения.
- Недоступная внешняя загрузка Gradle/Minecraft vanilla assets — инфраструктурная блокировка, а не физическая ошибка роя. Указывай точный URL/артефакт/кэш, фазу и stacktrace.
- `UP-TO-DATE` означает только состояние соответствующей Gradle-задачи, не прохождение всей клиентской сцены.

## 4. Phase 1 — закрыть real-client rendercheck

### 4.1. Как работает harness

Источник: `HybridRenderCheck.java`, test-only Fabric ClientModInitializer. Запускает окно Minecraft, открывает disposable fixture `DRMD-render-lab`, размещает тестовую сцену и по тикам последовательно проверяет:

| Веха `sceneTicks` | Событие / обязательная проверка |
|---:|---|
| 160/240 | Organic hybrid material и смена quarter-damage маски; `hybrid-before.png`, `hybrid-after.png`, `rendercheck-ok.txt` |
| 340–680 | Две настоящие ракеты отделяют дерево и колонну; визуальный полёт и физический наклон; `collapse-ok.txt` |
| 680–800 | Гибель дрона → одна пятисегментная ragdoll с артикуляцией и client sync; `ragdoll-ok.txt` |
| 840–856 | Роевой гравизахват удерживает **6** физических block bodies и выбрасывает все шесть |
| 930–946 | Тяжёлая гравирельса удерживает **7-cell** тело вдоль оси выстрела и запускает быстрее роя |
| 1010–1055 | Gravity shifter удерживает **2-cell** тело, создаёт направленную горизонтальную гравитацию, проверяет перемещение; `gravity-weapons-ok.txt` |
| 1065 | На клиенте присутствует ровно **128** живых дронов, созданных на сервере; плотный скриншот |
| 1080 | Скриншот дронов в полёте |
| 1085–1090 | Проверка движения/лимитов роевого индекса; `swarm-ai-ok.txt` и штатное завершение клиента |

Harness не входит в игровой release JAR. Он создаётся из source set `rendercheck`. Не переноси его entrypoints в production-мод.

### 4.2. Подготовка и запуск

`runRendercheck` автоматически зависит от `prepareRendercheckWorld`, а тот от `runGametest`. Поэтому можно запускать сразу основной task, контролируя его зависимости.

**Для локальной Linux-среды с доступными Xvfb и software OpenGL:**

```bash
# Прежде чем запускать, исключить ложный PASS от маркеров предыдущего прогона.
# Удалять только перечисленные генерируемые marker-файлы, НЕ пользовательские миры.
for name in rendercheck-ok collapse-ok ragdoll-ok gravity-weapons-ok swarm-ai-ok; do
  rm -f "build/rendercheck/${name}.txt"
done

LIBGL_ALWAYS_SOFTWARE=1 timeout 360s \
  xvfb-run -a ./gradlew runRendercheck --no-daemon --stacktrace
```

Контроль:

```bash
for name in rendercheck-ok collapse-ok ragdoll-ok gravity-weapons-ok swarm-ai-ok; do
  test -s "build/rendercheck/${name}.txt" || {
    echo "MISSING: ${name}.txt"
    exit 1
  }
done

cat build/rendercheck/swarm-ai-ok.txt
find build/rendercheck/screenshots -maxdepth 1 -type f -name '*.png' -printf '%f\n' | sort
find build/rendercheck/logs -type f -maxdepth 2 2>/dev/null | sort
```

**Осторожно:** `timeout` с кодом 124 означает дедлайн процесса; это не то же, что assert. Если отсутствует экран, драйвер OpenGL или ресурсы игры — классифицировать отдельно от падения физики. Не увеличивать лимиты бесконечно без вывода причин задержки.

### 4.4. Специальная приёмка Swarm AI: не имитировать успех

Подтверждённые значения непосредственно в коде:

```text
LIVE_SWARM_SIZE            = 128
MAX_BOID_NEIGHBOURS       = 32
MAX_BOID_CANDIDATES       = 96
Минимум движущихся дронов = 128 * 3 / 4 = 96
```

Проверка обязана подтвердить одновременно:

1. На сервере живы **все 128** ранее созданных дронов.
2. Клиент получил **ровно 128** объектов на контрольном кадре.
3. Не менее **96** имеют `getPhaseTimer() > 0.5` **и** `velocity.lengthSquared() > 0.0025`.
4. `indexedDrones >= 128`.
5. `maxCandidates <= 96`; суммарное число examined candidates за проход `<= 128 * 96`.
6. Все запросы в рамках одного прохода используют **один tick snapshot**.
7. Сцена не остановилась на ожидании `droneSwarmReady`, а штатно записала `swarm-ai-ok.txt` и завершила клиент.

Отдельный серверный GameTest в `DroneSwarmGameTests.java` индексирует **192** плотных дрона и проверяет границы поиска, один снимок за тик, позднее появление агента. **Не путать** это с визуальным 128-дроновым прогоном или с желаемым стресс-тестом 1k/5k/10k.

Нынешний `DroneSwarmAi` один раз на server-tick обходит `world.iterateEntities()` при формировании snapshot. Бюджет кандидатов ограничен, но массовое создание объектов `DroneEntity` всё ещё дорого. Не объявлять будущую packed simulation готовой.

### 4.5. Три разных класса ошибок

**A. Инфраструктура и ресурсы:** Gradle/Minecraft dependencies недоступны, нет ванильных assets, ошибки Xvfb/GL, процесс не запускается. Ремонтировать environment/caching, не менять игровой код. В протоколе указать заблокированный ресурс и повторный запуск после устранения причины.

**B. Синхронизация и жизненный цикл:** клиент видит меньше дронов/тел, ненадёжно загружается disposable-мир, неверный tick или позы не поступают в render. Проверять entity tracking, chunk tickets, spawn/discard, packet order, применимость World/Client thread, persistence и ready-флаги.

**C. Физика и gameplay assertions:** не набрались движущиеся агенты; joints не артикулируются; грави-поле не направлено; объекты не удержаны/не выстрелили; дерево не наклонилось. Исправлять конкретные расчёты/состояния с минимальным воспроизводимым тестом.

Не смешивать ошибку загрузки ресурса с ошибкой боидов и не обходить asserts путём создания фальшивых markers.

## 5. Phase 2 — сохранить и выпустить корректный Fabric JAR

В `.github/workflows/build.yml` pipeline уже определяет:

```text
checkout / Java 21
    ↓
./gradlew build runGametest
    ↓
LIBGL_ALWAYS_SOFTWARE=1 timeout 360s xvfb-run -a ./gradlew runRendercheck
    ↓
проверка пяти marker-файлов
    ↓
сохранение png/log/xml evidence
    ↓
копирование remapped JAR в dist/
    ↓
публикация GitHub Actions artifact drmd-6dof-pc
    ↓
обновление dist/ (на push; без гарантии при ошибке push)
```

### Правила packaging

- `build.gradle` содержит `packageTlauncher`, который зависит от `remapJar` и копирует `<archives_base_name>-<version>-fabric-1.21.1.jar` в `dist/`.
- Не распространять `-dev.jar`, `-sources.jar`, `-dev-shadow.jar` как устанавливаемый мод.
- При обновлении версии удалять **только** устаревшие build-generated `dist/drmd-6dof-*.jar` по определённому glob; не трогать код, исходные assets и установленные пользовательские моды.
- Установочный сценарий: Fabric Loader для Minecraft 1.21.1, Fabric API для 1.21.1, Java 21, одна актуальная версия DRMD в `mods/`.
- Не считать `[skip ci]` commit в `dist/` доказательством успешного реального клиента. Зафиксировать SHA исходного коммита, workflow run, артефакт и его контрольную сумму.
- Release marker-файлы и изолированные entrypoints не должны попадать в production JAR.

Пример проверки итоговых путей:

```bash
find build/libs -maxdepth 1 -type f -name '*.jar' -printf '%f %s bytes\n' | sort
find dist -maxdepth 1 -type f -name 'drmd-6dof-*-fabric-1.21.1.jar' -printf '%f %s bytes\n'
sha256sum dist/drmd-6dof-*-fabric-1.21.1.jar
```

Если в `dist/` окажется несколько конкурирующих «актуальных» jar или старый JAR с похожим названием, зафиксировать и исправить. Не загружать артефакт в пользовательские папки автоматически.

## 7. Следующие «жёлтые сектора» после зелёного P0/P1

**Не пытаться реализовать все одновременно.** Открывать следующий сектор только при зелёной интеграционной базе; для каждого сектора отдельная реализация, тест и видимое доказательство.

### 7.1. Физика / ragdoll / BlockBody

**Уже есть:** пять сегментов scout drone; массы и inertia, ball-socket constraints, NBT, network pose; ограниченные rigid block assemblies; локальное поле; адаптер разрушения опор.

**Доработать:**

1. Столкновения `ragdoll ↔ ragdoll`, `ragdoll ↔ BlockBody`, `BlockBody ↔ BlockBody`, если допустимы бюджеты.
2. Sleep/wake, simulation LOD и collision LOD для множества тел.
3. Контакты, friction/restitution, устойчивость при наклонных поверхностях и многократных ударах.
4. Разрушение/отделение связных частей сборки, пересчёт COM и inertia после удаления материала.
5. Адаптеры лёгких предметов/обломков в общем `PhysicsTarget`.
6. Новые rigs добавлять только после устойчивости первого; humanoid не выдавать за уже готовый.

**Приёмка:** детерминированные unit/серверные тесты импульса, столкновения, сохранения/загрузки и минимум одна клиентская демонстрация. Никакого неограниченного полного попарного поиска.

### 7.2. Физическое оружие — полировка, не новый физический движок

Сохранить три ветви:

| Вид | Поведение | Базовая проверка |
|---|---|---|
| Swarm grabber | Захват/удержание/залп множества лёгких объектов | 6 тел физически удерживаются и все запускаются |
| Heavy gravity rail | Удержание тяжёлого длинного тела, ориентация и мощный импульс | 7-cell body стабилен и запускается быстрее залпа |
| Gravity shifter | Захват тела, кратковременное локальное поле, бросок вдоль нового `down` | 2-cell body, горизонтальная траектория и корректный локальный вектор |

Следующие расширения, после базовой стабильности: prop-grab с предметами, веерный режим, безопасный захват взрывных props, рикошет, ударная волна, абляция/распад контейнеров, физические взаимодействия с обломками. Все действия — через единый contract `PhysicsTarget`, не через отдельные несовместимые `addVelocity` для каждого вида.

### 7.3. Boids и массовая сцена

**Текущее состояние:** пространственный bounded index работает как ограниченный поиск; AI ещё опирается на живые Minecraft `DroneEntity` и обход `world.iterateEntities()` при создании тик-снимка.

**Новая масштабируемая стадия:**

1. Packed swarm state для удалённых групп; `MobEntity` оставлять близкой боевой зоне.
2. Spatial hash / 3D partitions без O(N²); ограничивать candidate budget и полный rebuild cost.
3. Role-level group brain + local boids (separation / cohesion / alignment / target / obstacle avoidance).
4. Частотные уровни server AI; dormant state, wake conditions, simulation LOD.
5. Rendering batching/instancing или эквивалентное облегчённое представление дальних дронов.
6. Benchmark **1k / 5k / 10k** агентов на фиксированных сценах и оборудовании: TPS, MSPT, CPU/GPU frame time, FPS, memory, GC, draw calls, число полноценно симулируемых/отрисованных агентов.

**Приёмка:** отдельно оценить «сервер считает» и «клиент показывает». Не заявлять 10 000 как реализованную производительность без настоящего измерения на hardware/scene baseline.

### 7.4. Гибридная геометрия / quarter damage

**Уже есть:** явно размеченные organic materials, mesh с 3×3×3 кольцом соседства, 4×4×4 sparse damage-mask, baked модель, проверка до/после.

**Открыто:** происхождение материала (природный vs строительный), автоматическая разметка генератором без порчи построек, точное соответствие collision/raycast сетке, профили труб, повреждение moving body с пересчётом массы, секционное хранение masks и LOD после разрушения.

**Правило:** smooth только на выбранных органических поверхностях. Не сглаживать все каменные блоки мира; игроки строят из камня. Не умножать BlockEntity и mesh rebuild на число повреждённых микровокселей.

### 7.5. Порталы, зеркала, дальний обзор

**Сохранить архитектурное разделение:**

- `PortalTravel` — прохождение, трансформации позы, вектора скорости/roll/up, сетевой handoff.
- Portal see-through — реальное окно в пространство за поверхностью.
- Mirror — оптическое отражение с правильным handedness/winding и depth-aware маской.
- Distant Horizons — *опциональный* источник дальнего рельефного LOD; процедурный voxel horizon — не фактический 3D LOD объёмного мира.

**Незакрыто:** точная маска произвольного портала/зеркала, depth-occlusion, переход тел между измерениями со streaming/checks, proper volume LOD, снимки с высот 512/2048/8192, отсутствие накладывания фиктивного «планетного пола» поверх реальных DH LOD.

### 7.6. Реальный cubic world — долговременная миграция, не hotfix

Стратегическое решение: `16×16×16` — самостоятельная единица владения миром, независимые XYZ-координаты, целевой диапазон ~Y −50 000…+100 000. `CubicWorldSystem` с snapshots **не** заменяет ванильную жизненную модель. Перед объявлением реализации нужны:

1. Authoritative cube lifecycle, 3D tickets, eviction и транзакционные сохранения.
2. Volumetric generation без heightmap assumptions.
3. Engine-wide аудит Y-ограничений, BlockPos packing и секционных индексов.
4. Освещение/жидкости/тики/BlockEntity по граням кубов.
5. Сетевые cube subscriptions/deltas и клиентская mesh graph.
6. Миграция существующих миров с rollback; корректное различение отсутствующих и пустых кубов.
7. Объёмный LOD, коллизии и portal handoff.

**Не** пытаться объявить это готовым после теста сериализации `D6Volume` на больших Y. Совместимого готового drop-in CubicChunks engine для текущей указанной связки считать **не найденным, пока не доказано иное**.

## 12. Критерий остановки текущего задания

Текущий handoff считается выполненным **после** воспроизводимого полного прохождения тестовой цепочки и предъявления корректного JAR, либо после точной локализации внешнего блокера, не позволяющего запустить реальный Minecraft-клиент в данной среде. В последнем случае необходимы собранные исходники, падающая команда, точный диагностический лог, список непройденных тестов и явно обозначенные непроверенные состояния.

**Смысл текущей итерации:** закрыть разрыв между «компилируется» и «действительно работает». Сложные физические, AI и пространственные направления уже получили экспериментальные основы. Следующий этап не должен потерять их из-за очередной недоведённой контрольной сцены.
