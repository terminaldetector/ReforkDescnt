# Dynamic Boarding: опора на стыке движущихся палуб — 6 ноября 2026

Разработка и контрольные коммиты сохранены локально. Публикация в GitHub и запуск Actions приостановлены по текущему указанию пользователя. Это проверенный этап основного v8 и дополнения Dynamic Boarding / BlockBody; полного закрытия любого из этих ТЗ нет.

## Изменение

Основной код: `48a5e97682f59ea7d48e8897ccc804db33f7cda9`. Клиентский наблюдатель и точная ревизия сборки: `ffe7e75435d87b4d06584d7a7aa150f93efed794`. Указание о локальной работе сохранено отдельным коммитом `b7edb1dde1c7130e644227ff2ad2ccfa2b27c0b3`.

Прежний мотор назначал опорой последний подходящий корпус. При перекрытии корабельных полей гравитации новая принадлежность выбиралась по первому элементу списка. Пространственные индексы клиента и сервера не обязаны возвращать корпуса в одном порядке.

Теперь действующее поле гравитации сохраняет принадлежность, пока содержит игрока. При его отсутствии приоритет получает поле прежней опоры, затем стабильный идентификатор. Опора выбирается среди допустимых реальных контактов по расстоянию от точки под ногами до геометрии поверхности. При равных расстояниях учитывается нормаль; эквивалентные контакты сохраняют прежнюю опору, оставшиеся равенства разрешаются по идентификатору.

Проекция на реальную геометрию важна: на слегка наклонённой плоскости представитель контакта для расчёта импульса может находиться у угла стопы. Он продолжает использоваться для сил и скорости контактной точки; для выбора поверхности под ногами применяется отдельная проекция через существующий ориентированный коллайдер.

Решатель D6, контактные реакции, трение, условия отрыва и существующее наследование мировой скорости сохранены. Нового движка, привязки к сохранённой локальной позиции или телепортации вслед за корпусом нет.

## Воспроизведение и проверки

До исправления получены три отказа четырёх точечных проверок: зависимость стыка от порядка, выбор поля без прежнего владельца и захват опоры соседним краем. Первые логи/XML и тестовые исходники сохранены. Отдельный тест очень малого наклона затем воспроизвёл ошибку использования представительной точки решателя.

Первый серверный стенд ошибочно требовал удерживать конкретный корпус, хотя стопа касалась обоих. Диагностика показала скорость расхождения с первым контактом 0,1292 м/с при действующем пределе 0,1; второй ещё нёс нагрузку. Исправлена постановка стенда: начальное положение дальше от стыка; принадлежность проверяется до контакта со вторым корпусом и после полного пересечения края. В частично перекрытом состоянии обязательно сохраняется реальный контакт, но допустимо физическое перераспределение нагрузки. Исходные отказы, диагностические исходники и значения сохранены. Ранний пропуск аргумента в конструкторе тестового крепления сохранён как ошибка компиляции стенда.

Итог: **719 unit tests, 284 серверных GameTest**, без отказов, ошибок и пропусков. Восстановлен полный список тестов после отдельного диагностического прогона девяти BoardingGameTests; итоговые 284 проверены по XML и логу. Семь новых unit tests проверяют порядок кандидатов, реальную опорную поверхность, малый наклон, 40 последовательных шагов на стыке, приоритет/выход из поля и сохранение скорости при прыжке с наклонённой движущейся сборки. Новый серверный тест ведёт обычного игрока командами ходьбы через два физических корпуса с FixedJoint и сравнивает реальную позицию с публикуемыми координатами.

## Настоящий клиент на Cubic Chunks

Два независимых процесса: Minecraft 1.21.1, Fabric, Java 21, Better Cubic Chunks 0.1.1; лаборатория Y=2156. Mesa GL3.2/GLSL150 без Sodium и Mesa GL3.3/GLSL330 с Sodium 0.8.13. Это программная графика llvmpipe, не аппаратный бенчмарк Intel.

В каждом процессе повторно проходят пять сцен: связанные корпуса, Hinge/Motor, движущийся Slider с игроком, силовой разрыв крепления и проход между связанными движущимися палубами. Каждая сцена требует 90 свежих кадров с обоими реальными рендерами корпусов. Сохранено десять снимков; изображения прохода на обоих вариантах просмотрены, игрок и физические палубы видны.
