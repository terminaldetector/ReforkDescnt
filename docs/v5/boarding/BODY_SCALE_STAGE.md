# Масштабирование BlockBody — рабочий этап 1.1.29

Цель пользователя — полное исполнение всех ТЗ. Версии/JAR фиксируют проверку
изменений, не являются окончанием задачи. Большой UFO и общая приёмка12+9 ещё
не объявлены выполненными. Следующие зависимости: связность/отделение частей,
локальные функциональные модули → перевод существующего UFO и объёмный AI →
joints/ControlCore → полный игровой маршрут, dedicated/two-client и перезагрузка.

## Изменённые пределы и устройство

- 32768 занятых блоков на один физический корпус вместо256.
- Исходная world-selection до128×128×128 вместо16³. Локальные редактируемые
  координаты[-32,128) по каждой оси, включая запас для строительства назад.
- Один D6PhysicsBody на корпус. Независимые16³ секции локального коллайдера,
  неизменяемые BVH и небольшое дерево над секциями. Повреждение перестраивает
  только затронутые секции; предыдущий BodyMotion хранит прежнюю геометрию.
- Отдельный локальный AABB-индекс клеток для raycast. Пустота и отверстия в
  директории секций не становятся материалом. Общий мировой индекс1.1.28 сохранён.
- Реальный серверный `setLocalBlocks` атомарно проверяет пакет повреждений,
  один раз пересчитывает COM/геометрию, сохраняет мировые точки и их скорости.
  Неподдерживаемая клетка отклоняет весь запрос до изменения мира/массы.
- Registry-stable разреженный snapshot вместо4096 int на каждый куб пустоты.
  Сохранения прежнего cubic-volume формата читаются. Полная сетка32768 клеток
  занимает менее300КБ в проверенном однородном сценарии.
- Отдельный ограниченный cumulative journal максимум255 правок. При достижении
  256 обновляется базовая сетка. Новый/повторно отслеживающий клиент получает
  актуальную базу и журнал; полученная пачка пересобирает геометрию один раз.
  Это bounded delta sync, не бесконечно растущий лог. Boarding protocol4.
- Рендер пропускает внутренние блоки и закрытые грани; ванильные текстуры и
  сглаженные природные поверхности сохранены. HashMap-снимки избегают
  патологического open-addressing `Map.copyOf` на регулярных BlockPos-сетках.
- World collision запрашивает занятые секции, а не пустоту гигантского AABB.
  Vanilla baseTick использует маленькую proxy-оболочку pivot для своей служебной
  проверки жидкостей; реальная физика остаётся на композитной геометрии.
- Число подшагов учитывает фактическую скорость, инерцию, момент и момент силы,
  включая границу прецессии. Небольшой стабилизатор не означает постоянный spin2.
  Предел256 подшагов достаточен для разрешённого локального объёма/скоростей.
- Неизвестный объём останавливает интеграцию с сохранением импульса, а не
  изображает неупругий удар. Запросы не генерируют отсутствующие чанки.

## Найденные реальные проблемы

Первый полный клиентский прогон32К завис на добыче: Entity.baseTick сканировал
жидкости по всей широкой оболочке; thread dump показал World.getFluidState.
Далее открылись избыточные подшаги стабилизатора и MapN.probe на плотной сетке.
Логи/кадры первых попыток сохранены в work/body-scale и подлежат упаковке.

Большой клиент выявил расхождение ровно на один блок между реальной серверной
позицией игрока и cached motor feet. Прицел сервера и сетевой клиент работали
из разных глаз. Шаг сервера теперь начинает из фактического положения игрока,
сохраняя авторитетность контактов и внешние перемещения; телепортации к кэшу нет.
История предсказания актёра и корпуса использует одно ограниченное окно32.
Новый регрессионный тест проверяет внешнее collision-checked перемещение.
Первый вариант этого теста использовал world-UP без корабельного поля и после
отрыва закономерно терял lease; fixture исправлена добавлением конечного поля.
Порог пространственного совпадения не ослаблен.

## Проверка и незакрытая область

Новый настоящий клиент:32768 блоков, край128, обычные ЛКМ/ПКМ, Survival material,
пять сцен intact/cut/patched/hole/rebased,300 авторитетных сетевых правок,
непрерывный физический перелёт и предсказание; первый успешный рабочий прогон
дал242 подтверждения, max error0.08м, перелёт39.196м. Это рабочий прогон до
финального source commit, не exact-source выпуск. Полный свежий CI/native
фиксируется отдельно с source/JAR SHA и первыми провалами.

Этот этап не создаёт полные cube/chunk tickets для всего пространства корабля,
не вводит simulation LOD больших флотов, функциональные block entities,
фрагментацию, joints или управление UFO. Гидродинамика корпуса не реализована.
Рост лимита не является доказательством полного большого6DoF UFO с интерьером,
боевыми модулями, дронами, реактором и проверенным multiplayer/save-reload.

Полный локальный прогон кандидата:633 unit,183 GameTests,49 Python без ошибок.
Новый отдельный bodyscalecheck прошёл5 сцен и300 правок; actualFeetError=0,
216 подтверждений, max prediction error0.399694м при прежнем пороге0.8,
физический перелёт33.396м. Прогон до фиксации source SHA; результаты не
подменяют ожидаемый exact-source CI и native BCC.
