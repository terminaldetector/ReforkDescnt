## Voxy — хранение и LOD

Главная находка архива, но не тем, чем кажется: ценно **хранилище**, а не рендер.

**`StorageBackend`** — пять абстрактных методов и всё:

```java
MemoryBuffer getSectionData(long key, MemoryBuffer into);
void setSectionData(long key, MemoryBuffer data);
void deleteSectionData(long key);
void flush();
void close();
```

Ни одного типа Minecraft. Реализации: LMDB, RocksDB, Redis, in-memory. Поверх — компонуемые
адаптеры: сжатие, read-only кэш, фрагментация, условная и делегирующая обёртки. Это готовая
архитектура для Этапа 6, и её можно взять идеей, не трогая ни строчки чужого кода.

**`WorldEngine`** — секции по ключу с подсчётом ссылок:

```java
WorldSection acquire(int x, int y, int z, int lvl);
WorldSection acquire(long key);
WorldSection acquireIfExists(int x, int y, int z, int lvl);
```

плюс `MAX_LOD_LAYER`, колбэки `ISectionChangeCallback` / `ISectionSaveCallback`, `Mapper` (палитра
блочных состояний), `Mipper` (сведение уровня LOD вверх), `SectionSavingService`,
`VoxelIngestService` (приём настоящих чанков в хранилище).

**`WorldSection`** — плоский `long[] data`, уровень + x/y/z + упакованный ключ, состояние через
`VarHandle` (без блокировок), кэш переиспользования массивов. Видно, что писалось под нагрузку:
атомарность на VarHandle и ручной пул массивов — это про GC и про фоновые потоки.

**Рендер — не портируется.** 35 клиентских миксинов, из них 8 в Sodium и 11 в Iris. Это не
«компонент», это надстройка над внутренностями Sodium конкретной версии. Плюс сборка в архиве под
1.21.10.

**Вывод:** брать модель (backend-интерфейс, секция как `long[]` на уровне LOD, mip вверх,
ref-counting, ingest настоящих чанков). Не брать код и не пытаться портировать рендер.

## Immersive Portals — бесшовные переходы

**157 миксинов** (134 ядро + 18 peripheral + 5 misc) и 36 duck-интерфейсов. Куда бьёт:

```
29  client/render      11  client/sync       10  common/chunk_sync
 9  common/debug        8  common/collision   7  common/position_sync
 6  common/entity_sync  4  common/interaction  4  common/other_sync
```

Это перепрошивка конвейера «чанки — сущности — синхронизация позиции — рендер», а не библиотека, из
которой достают деталь. Вариантов ровно два: зависеть от него целиком или переизобрести конкретный
нужный трюк.

**И тут в плане противоречие.** Этап 1 предлагает изучать ImmPtl ради бесшовных переходов, а Этап 4
отменяет измерения. Если пространство одно вертикальное — портальная машинерия не нужна вовсе:
смотреть «сквозь портал» не во что. Настоящая задача при едином мире другая — стриминг чанков при
большой вертикальной скорости, то есть Этап 5. В DRMD переходы между слоями уже сделаны телепортом
на шве (`LayerBridge`) с фоновым прогревом (`SeamWarmup`), и экрана загрузки там нет.

## Chisels & Bits — дробление блока

Модульный: `api` / `core` / `create` вложенными jar'ами + платформенный слой (`scena`, тоже внутри).
API чистый и обобщённый — это его сильная сторона:

```java
interface IAreaAccessor {
    Stream<IStateEntryInfo> stream();
    IMultiStateSnapshot createSnapshot();
    IAreaShapeIdentifier createNewShapeIdentifier();
    boolean isInside(Vec3d);
}
interface IAreaMutator extends IAreaAccessor {
    Stream<IMutableStateEntryInfo> mutableStream();
    void setInAreaTarget(BlockInformation, Vec3d) throws SpaceOccupiedException;
    void clearInAreaTarget(Vec3d);
}
```

Читается как «область, по которой можно пройтись потоком записей состояния, снять снимок и
адресоваться дробным вектором вместо `BlockPos`». Для Этапа 11 это правильная форма API.

Оговорка: jar собран под intermediary (`class_243` = `Vec3d`, `class_2338` = `BlockPos`), то есть это
production-ремап, не dev-артефакт.

**Где цена.** API дешёвый, дорого — хранение: у C&B микроблоки живут в block entity на чанк-секцию.
Мир, где *любой* блок дробим и разрушаем (Этапы 10–11 вместе), — это уже не block entity, а
собственный воксельный слой, и он упирается ровно в Этап 6.

## Проблемы последовательности

1. **Этап 2 «портировать всё» — неверный второй шаг.** Портировать нечего: рендер Voxy прибит к
   Sodium, ImmPtl — это 157 миксинов, Tectonic Layers на другом загрузчике. Переносить надо
   *идеи и формы API*, выборочно, а не сборки.

2. **Этап 3 (разбиение на модули) до Этапа 6 — рано.** API Chunk Manager нельзя спроектировать
   раньше, чем известна модель хранения. Порядок должен быть обратным: сначала хранилище, из него
   вырастают границы модулей.

3. **Этапы 9–11 связаны в узел.** Хранение микроблоков определяет, что вообще может разрушение;
   физика динамических конструкций определяет, что обязаны уметь микроблоки. Делать их подряд как
   независимые — значит переписать дважды. Проектировать нужно один слой на троих.

4. **Этап 13 недооценён.** «Летающие блочные объекты как в Valkyrien Skies» — это не финальный
   штрих, а отдельный движок: свои системы координат, своя физика, свой рендер корабля, свои
   коллизии игрока на движущейся геометрии. По объёму это сопоставимо со всеми Этапами 5–8 вместе.

## Честно о масштабе

Собственные чанки, собственное хранилище, физический движок, микроблоки с разрушением и свой рендер
— это годы работы команды, не итерация мода. Это не повод не делать: это повод резать на куски,
каждый из которых works-on-its-own и даёт видимый результат, а не «через полгода всё вместе».

# Предлагаемый первый срез

**Этап 6 как отдельный модуль — хранилище LOD-секций — и подключить его к уже работающему
воксельному горизонту.**

Почему именно он:

- Горизонт сейчас рисует **процедурную** карту: правдоподобную планету, но не тот мир, над которым
  летали. С хранилищем он начинает рисовать **настоящий** рельеф — тот, что игрок видел, со
  всеми постройками, кратерами и следами.
- Модуль честно независим: интерфейс из пяти методов, ни одного типа Minecraft, тестируется без
  игры.
- Он же — фундамент Этапов 3, 5, 10, 11: границы модулей станут видны из него, а не из схемы.
- Результат виден сразу, в существующем моде, без переписывания всего остального.

Порядок внутри среза:

1. `SectionStorage` — backend-интерфейс по образцу Voxy (get/set/delete/flush/close), реализации:
   in-memory и файловая; адаптер сжатия.
2. `WorldSection` — `long[]` на уровень LOD, палитра состояний, mip вверх.
3. Ingest: настоящие чанки → секции уровня 0 при загрузке чанка на сервере.
4. Горизонт читает секции там, где они есть, и падает на процедурную карту там, где их нет.

**Сделано:** срез — [`SURFACE_STORE.md`](SURFACE_STORE.md). Ядро микроблоков и разрушения —
[`MICROBLOCKS.md`](MICROBLOCKS.md).

**Порталы** — отдельными установками поверх гравитационной песочницы (`GravityFields`), как фича, а
не как способ путешествия: колонка уже бесшовна, и Immersive Portals для неё не нужен.
