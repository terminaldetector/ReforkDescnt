# 4. Первый эксперимент: минимальный XYZ-генератор плотности

Соответствует разделу 4 брифа и шагу 6 "Порядка работы". Это первый шаг цикла, где ÆRis/Mirai
перестаёт быть только чтением источников и становится кодом — со всеми оговорками, которые это
означает в этой песочнице (см. ниже).

## Что сделано

Новый пакет `com.terminaldetector.drmd.aeris`, новая, полностью изолированная тестовая размерность
`drmd:aeris_test` — **не** трогает Overworld/Nether/End ни в одном режиме DRMD, ни одна существующая
система мода не гейтится и не проверяет её наличие.

- **`AerisDensity.java`** — сама `F(x,y,z)`. Ноль импортов Minecraft — целиком чистая Java. Два поля,
  объединённые через `max` (union): `sphereDensity` (сетка ячеек 48×48×48, в каждой ячейке по хешу
  независимо решается — есть ли сфера, где её центр, какой радиус — зажато так, чтобы сфера физически
  не могла вылезти за пределы своей ячейки) и `foamDensity` (пороговый 3D value-noise, ограниченный
  тем же типом ячеек — закрытый объём с пористой текстурой внутри, не бесконечная сплошная масса).
  Соглашение о знаке — как в ванильной `DensityFunction`: `≥0` — камень, `<0` — воздух.
- **`AerisDensityChunkGenerator.java`** — `extends ChunkGenerator`, интерпретирует `AerisDensity`
  напрямую как solid/air в `populateNoise`, без `NoiseRouter`, без `DensityFunction`, без аквифера,
  без правил поверхности — вся эта машинерия существует, чтобы формировать одну поверхность,
  производную от высоты (доки 01, раздел 1.3), а это ровно то допущение, отсутствие которого проверяет
  эксперимент. `Chunk`/`ChunkSection`/`ChunkPos` не тронуты — запись идёт через тот же
  `Chunk#setBlockState`, что использует любой обычный генератор.
- **`AerisMirai.java`** — регистрирует кодек генератора в `Registries.CHUNK_GENERATOR`, вызывается из
  `DescentMod.onInitialize()`.
- **`data/drmd/dimension_type/aeris_test.json`** + **`data/drmd/dimension/aeris_test.json`** — новая
  размерность, `min_y=-128, height=384` (то же число секций, что у ванильного Overworld — 24, просто
  сдвинутое, не новый непроверенный размер), фиксированный биом `minecraft:plains`.
- **`AerisDensityTest.java`** — единственный тест в этом проекте за всю сессию, который не мирует
  формулу копией, а вызывает настоящий продакшен-код напрямую: `AerisDensity` не зависит от Minecraft, поэтому мирить нечего.

## Как это устроено — и почему настолько минимально

Из вывода доки 01 (раздел 4, пункт 2): "не трогать `Chunk`/`ChunkSection`/`ChunkPos`, писать кастомный
`ChunkGenerator`". Из YUNG's Better Caves (doc 03) — рабочий прецедент честного вызова 3D-шума прямо на
(x,y,z) на текущей версии, но через `WorldCarver`, не через отдельный генератор. Здесь выбран путь
"полностью свой `ChunkGenerator`" (не `WorldCarver`, не подключение через `DensityFunction`-узел в
`NoiseChunkGenerator`) по трём причинам:

1. Самая буквальная реализация формулировки брифа — "generator directly interprets F(x,y,z) as
   solid/air" — без граничных эффектов интерполированной сетки `NoiseSettings.size_horizontal/vertical`
   (доки 01, раздел 1.2а), которые применились бы, если бы `F` шла через обычный `DensityFunction.sample`.
2. Даёт настоящие геометрические примитивы (сферы) — конкретно то, что бриф просит проверить отдельно
   от органических шумовых пятен, и что нельзя выразить только стандартными JSON-типами
   `DensityFunction` (нет примитива "расстояние до точки" в словаре ванильных типов).
3. Полностью избегает регистрации нового типа `DensityFunction` (свой `MapCodec`, интеграция в
   `NoiseRouter`/`ChunkGeneratorSettings`) — не меньший риск, чем регистрация `ChunkGenerator`, но без
   дополнительной выгоды, раз генератор всё равно нужен, чтобы дотянуться до `dimension` JSON.

Что специально не сделано в этом первом проходе, согласно прямому запрету брифа не пытаться несколько
систем сразу: **не** добавлена команда телепортации (см. ниже, почему), **не** используется настоящий
сид мира (плотность зафиксирована на константе — вопрос, который проверяет этот эксперимент, "работает
ли F(x,y,z) в реальном конвейере генерации вообще", а не "правильно ли она сидируется по миру"),
**не** тронуты Heightmap/освещение/рендеринг (это отдельные шаги 8–10), **не** добавлена гравитация/6DOF
для этой размерности (шаг, casus отдельный из раздела 9).

## Как туда попасть — сознательно без новой команды

Размерность зарегистрирована безусловно (как всегда существуют Nether/End), без переключателя в меню
и без гейта `WorldFeatures` — игрок, который туда не заходит, её не заметит. Чтобы посмотреть, оператору
достаточно ванильной команды, без единой строчки нового кода на телепортацию:

```
/execute in drmd:aeris_test run teleport @s 0 64 0
```

Своя команда телепортации (`ServerPlayerEntity.teleportTo(TeleportTarget)` или аналог) была рассмотрена
и осознанно отклонена для этого прохода — этот API уже без того один из наименее уверенных участков
всей сессии (см. секцию рисков ниже), и добавление ещё одной непроверенной сигнатуры ради удобства,
которое ванильная команда даёт бесплатно, не стоило того.

## Что проверено локально, а что нет

**Проверено локально, честно, реальным кодом** (`javac` + `junit-platform-console-standalone`, тот же
jar, что и весь остальной pure-logic testing этой сессии) — `AerisDensity` сама по себе, 4/4 теста
зелёные:

- в широкой выборке есть и камень, и воздух, камень — меньшинство (не залитое полупространство);
- **как минимум одна X/Z-колонка имеет 2+ раздельных участка камня по Y** — это прямая, не гипотетическая
  проверка на настоящей формуле центрального вопроса доки 01/02: может ли одна колонка держать
  несколько независимых поверхностей. Может — уже здесь, без какого-либо изменения `Heightmap` или
  хранилища.
- плотность нигде не убегает в бесконечность (сферы и пена ограничены по построению);
- детерминированность (одна и та же точка — один и тот же ответ).

**Компилировалось не локально — и не с первого раза.** `AerisDensityChunkGenerator` не удалось собрать
против настоящего classpath Minecraft/Fabric ни разу в этой песочнице (по-прежнему нет распакованного
Loom/Yarn-кэша — тот же вывод, что и в начале доки 01), так что каждая сигнатура метода была
реконструкцией по памяти и WebSearch, проверяемой только через реальный компилятор GitHub Actions.
Понадобилось 4 раунда, каждый — один конкретный, точный компиляторский вердикт, не гадание:

1. `NoiseConfig` лежит в `net.minecraft.world.gen.noise`, а не в `.gen.chunk`, как предполагалось по
   соседству с остальными gen-классами — 7 одинаковых ошибок "cannot find symbol", один и тот же
   символ, не расхождение сигнатур.
2. `populateNoise` не принимает `Executor` (память подсказывала более старую, ещё встречавшуюся в этой
   сессии сигнатуру с explicit executor) — заполнение теперь синхронное,
   `CompletableFuture.completedFuture(chunk)` вместо `supplyAsync`.
3. Метод для отладочного HUD называется `getDebugHudText`, не `addDebugScreenInfo` — эту точную
   сигнатуру компилятор сам назвал в сообщении "class is not abstract and does not override abstract
   method X", не пришлось гадать по second sources.
4. Не хватало отдельного `getWorldHeight()` без параметров — предположение, что высота генератора
   всегда приходит через параметр `HeightLimitView` на конкретный вызов, было неполным.

`getCodec()` и пакет `net.minecraft.world.ChunkRegion` (не `.gen.chunk.ChunkRegion`) были угаданы верно
с первого раза — второе благодаря прямому попаданию WebSearch, первое — просто повезло. Ни одна из этих
четырёх ошибок не была видна заранее ни при чтении кода, ни при рассуждении по памяти — все четыре
всплыли только на реальном компиляторе. Это само по себе небольшой, но конкретный аргумент в пользу
общего вывода ÆRis/Mirai о ценности "не заполнять догадками, проверять исходники": даже добросовестная
реконструкция по тренировочным знаниям плюс поиск даёт код, который выглядит правдоподобно и всё равно
не компилируется с первого раза в 3 случаях из 4 методов, где сигнатура вообще отличалась от
предположенной.

Совсем не проверено — визуально: сами сферы/пена, глазами, живым клиентом. Это то же ограничение, что
и во всей ÆRis/Mirai работе этой сессии — здесь нет живого Minecraft-клиента.
